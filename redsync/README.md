# 一、先理解什么是分布式锁

假设你有一个电商系统，多个服务实例同时处理同一件商品的库存。

商品库存是 1，两个请求几乎同时执行：

初始库存：1

请求 A

读取库存 = 1

判断库存充足

请求 B

读取库存 = 1

判断库存充足

结果：两笔请求都可能扣减库存

出现超卖，或者重复执行同一项任务

如果这段业务逻辑只能由一个请求同时执行，就可以使用分布式锁：

1. 请求 A 获取锁。
2. 请求 B 获取锁失败，等待或重试。
3. 请求 A 执行业务逻辑。
4. 请求 A 释放锁。
5. 请求 B 再尝试获取锁。

之所以叫“分布式”锁，是因为 A 和 B 可能运行在不同的服务器、容器或进程里，不能只依赖 Java 的 `synchronized`、Rust 的 `Mutex` 等进程内同步机制。

## 1. Distributed Locks with Redis：使用 Redis 实现分布式锁

原文核心意思：

在许多系统中，不同进程需要以互斥的方式操作共享资源，因此分布式锁是一个非常有用的基础机制。

目前有很多基于 Redis 的分布式锁实现，但它们采用的方案各不相同，有些简单方案提供的安全性保障较弱。Redis 官方因此介绍了一种更规范的算法，称为 Redlock，其目标是比单个 Redis 实例的方案提供更强的可靠性。

官方也列出了多种语言的实现，包括 Java、Python、Go、Rust、C++ 等。

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs



讲解：

这里要先区分两个概念：

- Redis 分布式锁： 一类实现方式的统称，可能只使用一个 Redis 实例。
- Redlock： Redis 官方提出的一种特定分布式锁算法，需要多个相互独立的 Redis 主节点。

所以，并不是所有 Redis 分布式锁都叫 Redlock。实际项目里常见的单实例 `SET NX PX` 方案，也属于 Redis 分布式锁的一种实现。

## 2. Safety and Liveness Guarantees：安全性与活性保证

原文提出，判断一个分布式锁是否有效，至少要关注三个性质。

| 性质                         | 中文解释    | 目标                               |
| -------------------------- | ------- | -------------------------------- |
| Safety：Mutual exclusion    | 安全性：互斥  | 同一时刻只能有一个客户端持有有效锁                |
| Liveness A：Deadlock free   | 活性：避免死锁 | 客户端崩溃后，其他客户端最终仍能获取锁              |
| Liveness B：Fault tolerance | 活性：容错   | 只要 Redis 节点中的多数仍可用，客户端就有机会获取和释放锁 |

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs

这三个性质非常重要。

### ① 安全性：不能有两个人同时持锁

假设 A 获取了锁，正在修改订单。此时 B 不应该再获得同一把有效锁并同时修改订单。

如果 A、B 同时执行关键业务，即使最终 Redis 中只有一个锁 Key，也不能说明业务执行过程是安全的。

### ② 活性：不能因为一个客户端崩溃而永久死锁

假设 A 获取锁后，服务器突然宕机。如果锁没有过期时间，锁可能一直残留，B 就永远无法获取它。

因此，锁一般需要设置 TTL（Time To Live，存活时间），例如 30 秒。即使客户端异常退出，锁最终也会自动过期。

### ③ 容错：部分 Redis 节点发生故障时，系统仍然能够工作

这正是 Redlock 引入多个独立 Redis 节点的动机之一。

但要注意：活性和安全性是不同的目标。 让系统最终能够继续运行，不代表在任何故障情况下都绝不会出现并发执行。

## 3. Why Failover-based Implementations Are Not Enough：为什么主从故障转移方案不够可靠？

这是全文第一个关键问题。

原文指出，很多 Redis 分布式锁采用以下架构：

- 一个 Redis 主节点负责获取和释放锁。
- 一个或多个从节点负责复制数据。
- 主节点故障时，从节点提升为新的主节点。

看起来有高可用保障，但问题在于：Redis 主从复制通常是异步的。

### 问题是怎么发生的？

步骤 1：A 获取锁

Redis 主节点 M 写入 lock:order:123，表示 A 已经获得锁。

步骤 2：主节点突然宕机

锁的写入还没复制到从节点 R。

步骤 3：从节点晋升为主节点

新主节点中不存在 A 的锁，因此认为该资源没有被锁定。

步骤 4：B 再次获取锁

A 可能还在执行任务，B 却成功获取了同一把锁，互斥性被破坏。

这就是 Redis 主从故障转移可能造成的双持锁问题。

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs



### 应该怎么理解？

主从复制解决的是数据冗余和故障恢复问题，但异步复制不能保证每一笔写入在主节点故障前都已经复制完成。

所以：

Redis 主从高可用 ≠ 分布式锁绝对安全。

不过，这并不意味着主从架构不能使用。假如锁只是为了避免重复计算，偶尔重复执行的代价不大，那么单实例加异步复制仍然可能是合理的工程选择。

## 4. Correct Implementation with a Single Instance：如何正确实现单实例锁

这一节非常实用，直接关系到日常开发中 Redis 锁的正确写法。

### 4.1 获取锁

原文使用的命令是：

```
SET resource_name my_random_value NX PX 30000
```

各个参数的含义如下：

| 参数                | 作用                         |
| ----------------- | -------------------------- |
| `resource_name`   | 锁的 Key，例如 `lock:order:123` |
| `my_random_value` | 当前客户端生成的唯一锁标识              |
| `NX`              | 只有 Key 不存在时才设置成功           |
| `PX 30000`        | 设置过期时间为 30,000 毫秒，也就是 30 秒 |

这条命令将获取锁的判断和写入合并为一次原子操作。

假设 A 和 B 同时执行这条命令：

- A 先成功写入 Key，得到 `OK`。
- B 发现 Key 已经存在，获取失败。

因此，在同一个正常工作的 Redis 实例上，这种方式可以避免两个客户端同时成功创建同一把锁。

### 4.2 为什么必须使用随机值？

很多初学者会写成：

```
SET lock:order:123 1 NX PX 30000
```

这种写法的问题是，所有客户端使用的锁值都是 `1`，无法区分锁的归属。

应该改成类似：

```
SET lock:order:123 8f4a7c2d NX PX 30000
```

其中 `8f4a7c2d` 只是示例，实际应使用足够随机、不会重复的标识。

### 4.3 为什么不能直接 DEL 释放锁？

假设发生以下情况：

1. A 获取锁，锁的值是 `token-A`。
2. A 因为某种原因执行了 40 秒，锁在 30 秒后自动过期。
3. B 在第 31 秒获取了新锁，锁的值是 `token-B`。
4. A 在第 40 秒恢复执行，并调用 `DEL lock:order:123`。

此时 A 删除的其实是 B 的锁！

正确的释放方式必须是：只有锁的值仍然等于自己的唯一标识时，才允许删除。

Redis 8.4 及以上版本可以使用 `DELEX` 命令：

```
DELEX lock:order:123 IFEQ token-A
```

对于较早的 Redis 版本，可以使用 Lua 脚本：

```
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

调用时：

- `KEYS[1]`：锁的 Key。
- `ARGV[1]`：当前客户端获取锁时生成的随机值。
- 返回 `1`：成功删除自己的锁。
- 返回 `0`：锁不存在，或者锁已属于其他客户端。

由于 Lua 脚本在 Redis 中原子执行，检查锁值和删除操作之间不会被其他 Redis 命令插入。

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs



这一节的重点：获取锁要原子化，释放锁也要原子化，而且只能释放自己的锁。

### 4.4 TTL 到底意味着什么？

TTL 不只是锁的自动清理时间，也是当前客户端能够安全执行受保护操作的时间窗口。

例如，锁的 TTL 是 30 秒：

- A 获取锁后，正常执行了 2 秒，释放锁。
- B 随后获取锁并执行任务。
- 如果 A 被系统暂停了 40 秒，醒来时锁早已过期，那么 A 不能再假定自己仍然拥有锁。

这里有一个非常重要的区别：

Redis 自动释放了锁，并不意味着原来的业务线程也会自动停止执行。

这也是后面 Redlock 讨论的核心问题之一。

## 5. The Redlock Algorithm：Redlock 算法

单实例锁的实现很简单，但它仍然依赖单个 Redis 节点。为了解决部分节点故障带来的问题，Redis 官方提出 Redlock。

### 5.1 Redlock 的基本架构

假设有 5 个完全独立的 Redis 主节点：

客户端 A

使用同一个 Key 和同一个随机锁标识

R1

独立节点

R2

独立节点

R3

独立节点

R4

独立节点

R5

独立节点

获取成功的判定条件

# 至少 3 / 5 个节点

并且获取多数锁所花费的时间必须小于锁的有效期。

这里的关键是：这 5 个节点不是一个主从集群的 5 个成员，而是用于 Redlock 算法的 5 个相互独立的 Redis 主节点。

### 5.2 获取锁的完整流程

原文规定了以下步骤。

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs



1. 记录开始时间。 客户端读取本地时间，精确到毫秒。
2. 并行尝试获取 5 个节点的锁。 使用相同的 Key、相同的随机值，以及较短的单节点请求超时时间。
3. 检查是否获得多数锁。 5 个节点至少有 3 个返回成功。
4. 检查总耗时。 如果获取多数锁花费的时间已经超过 TTL，即使获得了 3 个节点，也不能认定获取成功。
5. 计算剩余有效时间。 从原始 TTL 中扣除获取锁所消耗的时间，并预留一定的时钟误差余量。
6. 获取失败则清理。 尝试释放所有节点上可能已创建的锁，避免残留锁一直占用资源。

### 5.3 为什么必须获取多数节点？

因为多数派具有一个重要的数学性质：任意两个多数派至少有一个共同节点。

以 5 个节点为例：

- A 获取到 R1、R2、R3。
- B 想要获取锁，至少也要拿到 3 个节点。
- 如果 A 的锁仍在有效期内，B 无法在 R1、R2、R3 中的任何一个成功设置同一把锁。
- R4、R5 只有两个节点，不足以让 B 达到 3 个节点的门槛。

因此，在算法所要求的时间与故障假设成立时，多数派交集有助于保证互斥性。

需要注意：多数派交集本身并不能消除所有故障风险。 如果节点的锁提前过期、客户端被长时间暂停，或者时钟出现异常，情况就可能变得复杂。

### 5.4 为什么要扣除获取锁所花费的时间？

假设 TTL 是 10 秒。

A 从开始获取锁到获得多数节点的响应，已经花费了 2 秒。

那么 A 不能认为自己还拥有完整的 10 秒，而应当将剩余有效时间估算为：

\\[ T\_{\text{remaining}} = T\_{\text{TTL}} - T\_{\text{elapsed}} - T\_{\text{margin}} \\]

其中：

- \\(T\_{\text{TTL}}\\)：最初设置的过期时间。
- \\(T\_{\text{elapsed}}\\)：获取锁所花费的时间。
- \\(T\_{\text{margin}}\\)：用于预留时钟漂移等误差的安全余量。

例如，TTL 为 10 秒、获取耗时为 2 秒、安全余量为 100 毫秒，那么剩余有效时间约为 7.9 秒。

实际实现还需要考虑客户端暂停、网络延迟和业务执行时间，不能只看这一个计算公式。

## 6. Is the Algorithm Asynchronous?：这个算法是异步的吗？

原文讨论了一个重要前提：Redlock 依赖于不同机器上的本地时钟以大致相同的速率前进，并假定时钟漂移相对于锁的有效期足够小。

这意味着 Redlock 并不是在任何时间条件下都能无条件保证互斥。它的安全性依赖于一定的时钟和执行时间假设。

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs



举个例子：

A 获取了一个 10 秒的锁，但在执行任务时，进程被暂停了 15 秒。

在暂停期间：

- Redis 中的锁已经过期。
- B 可能成功获取同一把锁。
- A 恢复执行后，可能仍然继续执行原来的业务。

于是，A 和 B 可能同时操作共享资源。

这不是简单调整 TTL 就能彻底解决的问题，因为进程暂停的时间可能超出预期。

## 7. Retry on Failure：获取锁失败后如何重试

原文建议，获取锁失败的客户端应等待一个随机时间后再重试，而不是立即不断争抢。

例如：

```
A：获取失败 -> 等待 100 ms -> 重试
B：获取失败 -> 等待 250 ms -> 重试
C：获取失败 -> 等待 180 ms -> 重试
```

这里的数字只是示例。

这样做的目的，是减少多个客户端同步重试、持续竞争的情况。

另外，原文特别强调：如果客户端只获取到了部分节点的锁，却没有成功获得多数派，就应该尽快释放这些部分获取的锁，不要等到它们全部自然过期。

实际开发中还应设置最大重试次数或整体等待期限，并使用随机退避策略，避免锁竞争造成大量请求堆积。

## 8. Releasing the Lock：释放锁

Redlock 的释放过程与单实例锁的基本原则相同。

客户端需要向相关 Redis 节点发送释放操作，并且只能删除值与自己随机标识相匹配的锁。

即使客户端认为某个节点上的锁没有获取成功，也可以尝试执行安全的释放操作。

为什么？

因为客户端可能遇到网络超时：Redis 实际上已经执行了 `SET`，但成功响应没有及时到达客户端。客户端无法仅凭超时判断服务端是否真的没有写入锁。

安全的条件删除操作可以处理这种不确定性，而不会误删其他客户端的锁。

## 9. Safety Arguments：Redlock 为什么被认为能够保证安全性

Redis 官方通过多数派交集和锁的剩余有效时间来解释互斥性。

核心思路是：

1. 客户端成功获取多数节点的锁。
2. 在剩余有效时间内，这些节点的锁仍同时有效。
3. 另一个客户端不可能同时获得足够数量的同一批有效锁。
4. 因而，在满足算法假设的有效时间窗口内，两个客户端不能同时成功获得同一把锁。

但要记住，这个论证依赖于前面提到的时钟漂移、锁有效期和获取耗时等假设。Redis 官方文档后面也明确提醒开发者注意时钟问题和 fencing token。

## 10. Liveness Arguments：Redlock 如何避免死锁

原文列出三个主要机制：

- 自动过期： 锁的 TTL 到期后，其他客户端有机会重新获取锁。
- 主动释放： 获取失败或者业务完成后，客户端尽快清理锁。
- 随机退避： 失败的客户端随机等待后重试，减少竞争。

不过，网络分区可能导致客户端无法释放已获取的锁。此时系统可能需要等待 TTL 到期才能重新获取锁。

如果网络故障持续不断，系统的可用性也可能持续受到影响。

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs



这说明 Redlock 的设计是在安全性、可用性和复杂度之间做权衡，而不是保证任何故障下都立即可用。

## 11. Performance, Crash Recovery and fsync：性能、崩溃恢复与持久化

这部分讲的是另一个容易被忽略的问题：Redis 节点重启后，可能忘记之前持有的锁。

假设 A 在 5 个节点中的 R1、R2、R3 成功获取锁。随后 R1 崩溃并重启，但锁数据没有被持久化保存。

如果 R1 很快重新加入可用节点集合，另一个客户端 B 就可能从 R1、R4、R5 获取到 3 个锁，而 A 的锁仍在 R2、R3 上。

此时就可能出现两个客户端都认为自己持有锁的情况。

Redis 官方讨论了以下措施：

- 使用 AOF 等持久化机制降低锁丢失的风险。
- 如果需要抵御崩溃后丢失数据的情况，可以考虑 `fsync=always`，但这会增加持久化开销。
- 也可以让发生崩溃的节点等待超过最大 TTL 后再重新参与锁服务，确保之前的锁已过期。

具体采用哪种方式，需要结合可用性要求、持久化配置和性能需求来决定。

## 12. Making the Algorithm More Reliable: Extending the Lock：延长锁的有效期

有些任务无法在固定的短 TTL 内完成，因此需要续期机制。

例如：

- 初始锁的有效期为 10 秒。
- 业务执行到第 8 秒时，还没有完成。
- 客户端尝试延长锁的 TTL。

Redis 官方建议，续期时不能无条件执行 `PEXPIRE`。客户端必须先确认锁仍存在，并且锁的值仍然是自己最初设置的随机标识。

只有在多数节点上成功延长，并且满足相应的有效时间要求后，客户端才能认为续期成功。

原文还强调，续期次数应当受到限制，以免无限续期破坏系统的活性保证。

这里尤其要注意：续期失败时，客户端必须停止将自己视为锁的持有者，并且不能继续不受保护地修改共享资源。

# 三、原文最值得关注的争议：Redlock 到底安全吗？

文章最后有一个非常重要的提示：Redis 官方建议读者阅读 Martin Kleppmann 对 Redlock 的分析，以及 Redlock 作者 antirez 的回应。

这不是一个可以忽略的附录，而是理解分布式锁时必须了解的争议。

## 1. Martin Kleppmann 的主要观点

Kleppmann 认为，如果分布式锁用于保护数据正确性，那么仅靠锁的 TTL 和 Redlock 的多数派机制仍然不够。

他的核心论点是：客户端可能在持锁期间暂停很久，等它恢复时，锁已经过期，另一个客户端也已经取得了新锁。旧客户端却可能继续写入数据。

详细分析见：[How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html?utm_source=chatgpt.com)。

[image](https://www.google.com/s2/favicons?domain=https://martin.kleppmann.com\&sz=32)

## 2. 什么是 Fencing Token（栅栏令牌）？

这是理解争议的关键。

栅栏令牌是一个随着每次获取锁而严格递增的数字，用于让真正保存数据的服务拒绝旧客户端的过期操作。

例如：

## 33

A 获取锁，令牌为 33

A 被系统暂停，锁到期。

## 34

B 获取新锁，令牌为 34

B 先完成写入，数据存储系统记录已接受的令牌为 34。

A 恢复后尝试写入，令牌仍为 33

存储系统发现 33 小于 34，因此拒绝这次过期写入。

这个机制与随机锁值有本质区别：

- 随机值用于确认“这是不是我创建的锁”。
- 栅栏令牌用于判断“这次业务操作是不是比已经接受的操作更新”。

但还有一个关键前提：栅栏令牌必须由可信的协调机制生成，并且由真正保存业务数据的系统进行校验。 只是在客户端检查令牌是否过期，并不能提供同等保障。

Kleppmann 指出，Redlock 本身并不提供每次获取锁都严格递增的令牌，因此不能仅凭 Redlock 成功，就认为共享资源的写入一定安全。

## 3. Redlock 作者的回应

Redlock 作者 antirez 不同意 Kleppmann 对算法的全部批评。他认为 Redlock 的设计目标，是在单实例或主从故障转移方案之上，构建一个更可靠、复杂度相对可控的分布式锁系统。

双方争论的核心是：在现实系统的时钟、网络延迟和客户端暂停等条件下，Redlock 能够提供多强的安全性保障，以及它是否适合对数据正确性有严格要求的场景。

可以阅读作者的回应：[Is Redlock safe?](https://antirez.com/news/101?utm_source=chatgpt.com)。

我的建议是，不要把这个争论简化为“Redlock 完全没用”或“Redlock 绝对安全”。真正需要回答的是：如果锁失效，业务会发生什么？你能否在数据写入层面阻止旧客户端继续操作？

# 四、实际项目应该怎么选？

下面是我对常见业务场景的建议。

| 场景                | 推荐方向                                  | 关键考虑            |
| ----------------- | ------------------------------------- | --------------- |
| 防止重复计算、重复发送非关键通知  | 单实例 Redis 锁                           | 偶尔重复执行可以接受      |
| 定时任务多实例竞争         | Redis 锁 + 幂等机制                        | 避免重复执行和锁过期后继续执行 |
| 同一订单避免并发更新        | 数据库事务、条件更新、乐观锁                        | 最终一致性必须由数据层保障   |
| 库存扣减、余额变更         | 原子 SQL、事务、约束、幂等设计                     | 不应只依赖 Redis 锁   |
| 对强协调和锁所有权有严格要求的任务 | ZooKeeper、etcd 等协调系统，结合 fencing token | 还要确保业务存储端校验令牌   |

如果你正在开发普通的后端服务，我建议从下面几个原则开始：

1. 使用 `SET key token NX PX ttl` 获取锁。
2. 使用唯一 token 和原子条件删除释放锁。
3. 设置合理的 TTL，并考虑续期、超时和异常退出。
4. 对重要业务使用幂等键、数据库事务或条件更新。
5. 如果旧客户端绝不能在锁过期后继续写入，设计 fencing token，并由存储端拒绝旧令牌。

最重要的一点：Redis 锁可以帮助协调客户端，但不能代替业务数据本身的一致性保障。

如果你希望深入理解这篇文章，我建议下一步重点研究“锁过期后的旧客户端为什么还能写数据”以及“如何用数据库条件更新或 fencing token 解决这个问题”。这两个问题比单纯记住 Redlock 的五个步骤更有实际价值。
